# Stage 4 說明：官方歷史轉乘需求整合

## 1. 為什麼加入這份歷史資料

自行蒐集的即時快照適合研究「某站未來還剩多少車」與缺車／滿站風險，但需要等待真實時間累積。臺北市政府另外提供 2023 年轉乘 YouBike 租借資料，可立即分析歷史需求、平假日差異、熱門站點與騎乘時間。

兩種資料用途不同：

| 資料 | 最適合的問題 | 不適合直接回答的問題 |
|---|---|---|
| 2023 轉乘租借歷史資料 | 每小時轉乘需求、平假日型態、熱門借還站 | 全體使用者需求、30 分鐘站點庫存 |
| 自行蒐集即時快照 | 15／30／60 分鐘站點庫存與缺車風險 | 尚未累積完成前的長期季節型態 |

因此本專案採用 hybrid data strategy，不用其中一份資料取代另一份。

## 2. 官方來源與範圍

- 資料集：[臺北市轉乘YouBike租借資料](https://data.gov.tw/dataset/169174)
- 提供機關：臺北市政府交通局
- 授權：政府資料開放授權條款第 1 版
- 本階段月份：2023 年 1 月
- 原始檔大小：約 71 MB
- 原始資料列：593,616

官方說明指出，資料只包含與公車或捷運轉乘有關的 YouBike 租借紀錄，且 2023 年後不再更新。因此分析結果不能直接代表全體 YouBike 使用者或目前 2026 年的需求水準。

來源與下載網址集中記錄在 `config/historical_sources.json`，大型 CSV 本身由 Git 忽略。

## 3. 真實欄位與時間粒度

| 官方欄位 | 清理後欄位 | 用途 |
|---|---|---|
| 借車時間 | `borrow_time` | 借車小時 |
| 借車站 | `borrow_station` | 起點站名稱 |
| 還車時間 | `return_time` | 還車小時 |
| 還車站 | `return_station` | 終點站名稱 |
| 租借時數 | `duration_minutes` | 實際騎乘分鐘數 |
| 借車日期 | `borrow_date` | 日曆日期 |

雖然欄位名稱是「時間」，實際檔案的分鐘與秒全部為 0，只保留小時。這代表資料適合 hourly demand analysis，不能從它建立精確的 30 分鐘 target。

## 4. 清理與品質決策

### 時間與騎乘長度

- 借還時間統一轉換為 `Asia/Taipei`。
- `租借時數` 解析為分鐘。
- 原始借車日期與借車 timestamp 日期一致性會被檢查。
- 超過兩小時的騎乘被標記但保留，不會在未驗證前任意刪除。

### 重複列

完整資料有 1,611 筆「額外完全相同列」。資料沒有 ride ID，同一小時內可能真的有不同使用者走相同路線且騎乘長度相同，因此不能安全地把相同列當成重複錯誤。管線會標記並在品質報告揭露，但保留所有紀錄。

### 站名對應

歷史站名會進行 Unicode、空白、`YouBike2.0_` 前綴與「台／臺」正規化，再與目前官方快照比對，不使用模糊配對：

| 指標 | 結果 |
|---|---:|
| 歷史站名 | 1,784 |
| 可對應現行站名 | 1,208 |
| 借車紀錄對應率 | 99.08% |
| 還車紀錄對應率 | 95.99% |

唯一站名對應率較低但逐筆對應率很高，表示大量交易集中在仍存在的主要站點；未匹配名稱多半是少量、改名或已撤除站點。未匹配資料仍保留。

## 5. 一月 Historical EDA 結果

### 每日需求

| 類型 | 天數 | 平均每日轉乘租借 |
|---|---:|---:|
| 平日 | 22 | 20,670.8 |
| 週末 | 9 | 15,428.8 |

這是描述性結果，尚未控制元旦假期、春節、天氣或資料族群差異。

### 小時型態

平日最高時段：

1. 18:00，平均約 2,056 筆／日
2. 08:00，平均約 2,021 筆／日
3. 17:00，平均約 1,686 筆／日

週末最高時段集中於 14:00–18:00，其中 17:00 最高，平均約 1,330 筆／日。

這與通勤轉乘族群的預期相符，但只能描述此資料集，不構成因果證明。

### 騎乘時間

| 百分位 | 分鐘 |
|---|---:|
| 25% | 4.50 |
| 中位數 | 7.25 |
| 75% | 13.68 |
| 95% | 45.89 |
| 99% | 121.22 |

最長紀錄約 1,105 分鐘，屬於需要後續 error analysis 的極端值，因此只在視覺化時截到第 99 百分位，原始紀錄並未刪除。

## 6. 如何重現

下載官方一月資料：

```bash
python src/download_historical.py --month 2023-01
```

清理並產生報告：

```bash
python src/prepare_historical.py
```

開啟：

```text
notebooks/04_historical_demand_analysis.ipynb
```

執行全部測試：

```bash
python -m unittest discover -s tests -v
```

## 8. 對模型設計的影響

本資料可以建立一個清楚標示範圍的 hourly transfer-demand baseline，例如預測「某站下一小時的轉乘借車筆數」。它不能被拿來假裝是全體需求，也不能直接與 2026 即時庫存快照逐列合併，因為年份、族群與 target 定義都不同。

較合理的後續安排：

1. 擴充至 2023 其他月份，檢查季節與月份一致性。
2. 加入 2023 天氣資料，建立 hourly historical baseline。
3. 將歷史站點型態作為背景資訊，而不是直接當作 2026 即時 target。
4. 即時快照持續負責 30／60 分鐘 availability 模型。

## 9. 作品集口頭說明範例

> 我沒有因為即時 API 缺少歷史檔就忽略官方歷史資料，而是把兩種資料分工。2023 歷史檔只涵蓋轉乘使用者，而且時間被聚合到小時，所以我用它分析 hourly demand、通勤尖峰與站點活動；2026 自行蒐集快照則用於站點可借車數的短期預測。這樣可以利用現成歷史資料，同時避免把不同族群、年份和 target 混成同一個模型。
